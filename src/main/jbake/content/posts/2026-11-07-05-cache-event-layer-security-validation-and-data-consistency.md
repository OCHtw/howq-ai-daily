AI大大針對先前系統的快取緩存架構基礎(<a href="https://dev.howqpon.com/posts/2026-11-03-22-implementing-secure-cloud-web-application-architecture-designs-4-cache-and-buffer-layer.html?utm_source=howqpon.com" target="_blank" rel="noopener noreferrer">快取緩存事件層 ↗</a>)：Redis L2 Read、RabbitMQ 非同步寫入、CQRS、最小權限、HMAC／nonce／message-id，以及 DB 提交後的快取更新。AI大大整理「必要安全修正」與「可選效能優化」兩欄，先列出最可能造成資料不一致或權限繞過的缺口，並為每項補上可驗證的測試情境。

### 修正與驗證清單

左欄依風險優先排序；右欄為相關的可選優化，不能取代左欄的正確性保證。

| 必要安全修正（含資料一致性） | 可選效能優化 |
|---|---|
| **① Consumer 獨立授權**：不能只驗 HMAC。若 Web 主機持有簽章金鑰，入侵者仍能產生合法簽章。Consumer 須核對可信身分、租戶、資源所有權、命令與可修改欄位。**測試：**以有效簽章修改別家店、其他租戶或提高自身權限；全部拒絕，DB 無異動並留下稽核紀錄。 | **授權資料短期快取**。**測試：**撤銷管理權後，須在約定期限內開始拒絕命令。 |
| **② DB 異動、去重紀錄及 Outbox 同交易**：業務資料、已處理 message-id、待發布快取事件一起提交；Consumer 提交成功後才 ACK。**測試：**在提交前、提交後但 ACK 前、事件發布前終止服務；恢復後業務只生效一次，事件仍可補送。 | **批次提交與批次發布**。**測試：**批次混入失敗資料，不得 ACK 未提交訊息；再比較吞吐與延遲。 |
| **③ 防止舊版本覆蓋新版本**：命令定義預期版本及衝突處理；快取更新採版本比較與原子操作。僅在提交後刪快取，仍可能被較早開始的回源請求填回舊值。**測試：**讓 v12 先於 v11 到達，並延遲舊回源請求至新資料提交、失效後才完成；DB 與快取不得倒退，刪除資料不得復活。 | **依實體分流、合併重複 Reload**。**測試：**熱點資料持續更新並增加 Consumer；積壓降低，亂序測試仍通過。 |
| **④ 區分已受理與已完成**：使用持久訊息、持久佇列、publisher confirms，並處理無法路由的訊息。確認遺失時，以相同業務冪等鍵重試。**測試：**移除 binding、重啟 Broker、切斷 confirm 回程；不得誤報業務完成，重試不得重複建立資料。 | **非同步／批次 confirms、調整 prefetch**。**測試：**比較吞吐、記憶體與待確認數量，故障後的可靠性結果須相同。 |
| **⑤ 分開定義防重放與業務冪等期限**：明定 timestamp 窗口、時鐘偏差、nonce 原子登記與金鑰輪替；簽章涵蓋命令、目標、身分、內容及識別碼。可信受理後的內部重送須與外部重放分開處理。去重期限涵蓋最長重試及死信重送期間。**測試：**跨節點併發重送、篡改內容、超時重放、合法訊息長時間排隊及隔日死信重送；非法請求拒絕，合法命令最多生效一次。 | **入口 nonce 快速檢查**。**測試：**清空 nonce 快取後重送已執行訊息，持久業務去重仍須阻止重複異動。 |
| **⑥ 有限重試與受控死信重送**：暫時錯誤採退避及次數／時間上限；非法簽章、無權限、格式錯誤不得無限 requeue。死信須可告警、查詢、稽核及受控重送，保留原業務識別碼，並驗證死信轉送可靠性。**測試：**DB 中斷、毒訊息、DLQ 不可用；不得高速重試、阻塞其他命令或靜默遺失，恢復重送後不得重複生效。 | **重試佇列分級、故障期間暫停消費**。**測試：**DB 停機十分鐘後恢復，不得因重試流量瞬間壓垮 DB。 |
| **⑦ Redis 唯讀例外交給獨立身分**：Web 不得為 nonce、LOADED、TTL 延長、Reload 或 Invalidate 取得寫權。由專用服務處理，明列命令、Key 與 Pub/Sub channel 權限。**測試：**以 Web 真實憑證執行 SET、DEL、EXPIRE、寫入腳本、跨範圍讀取及未授權訂閱；全部拒絕，合法讀取與專用更新服務正常。 | **Pipeline／MGET**。**測試：**混入允許與禁止的 Key，不得洩漏跨租戶資料，再比較延遲。 |
| **⑧ 漏通知與訊息遺失可補償**：Keyspace Notifications 僅作提示；以持久事件、版本／水位對帳及快取重建保底。LOADED 綁定資料版本，資料消失時不得仍視為完整載入；本地快取也須有失效上限。**測試：**中斷訂閱、漏送更新、清空 Redis、保留 LOADED 但刪除資料；須在約定期限內偵測並修復，不得永久回傳舊值或假空值。 | **TTL 隨機偏移、熱門 Key 合併回源、短期負快取**。**測試：**大量 Key 同時到期或大量查詢不存在資料時，回源受限；新增資料後負快取須按期失效。 |

### 驗收前須訂定的參數

| 參數 | 必須明確定義的內容 |
|---|---|
| 入口有效窗口 | timestamp 可接受多久以前及多久以後的請求 |
| 時鐘偏差 | 節點容許偏差，以及超出時的處理 |
| nonce 保留期 | 涵蓋有效窗口與時鐘偏差；登記須為原子操作 |
| 最大重試期間 | 重試次數、退避方式、總時間與進入死信條件 |
| 業務去重保留期 | 涵蓋自動重試、人工死信重送及補償期間 |
| 最大舊資料時間 | 各類資料可接受的快取延遲；權限資料另訂撤權期限 |
| 補償完成期限 | 漏事件、版本落後及快取重建須多久內完成 |
| 成功狀態 | 明確區分已受理、處理中、已提交、失敗與待補償 |

### 實作優先順序

1. 先完成 Consumer 授權、交易內去重與 Outbox、版本防倒退。
2. 再完成發布確認、防重放、重試與死信。
3. 補齊 Redis 權限驗證、漏事件對帳與快取重建。
4. 通過故障測試後，再調整批次、prefetch、分流與 TTL。
